# 命令身份、执行范围与权限

## 三种身份

- `LocalOperator`：本地进程控制者。GUI 管理操作、Headless 控制台及经过 Bearer 认证的本机 HTTP 使用同一身份，控制本进程。
- `Player`：世界中的玩家。本地房主与远程玩家没有身份或权限差别；从连接已验证的存档主体读取权限，不根据连接顺序、设备或 IsLocalCharacter 提权。
- `System`：内部自动流程。网络及 HTTP 请求不能自行声明该身份。

本地控制者与玩家可以是同一个人，但调用路径分别表达不同身份。GUI 玩家命令栏的世界／服务器操作仍使用 Player；本地应用设置使用 LocalOperator。认领服务器只授予玩家标准权限管理与再授权能力，不赋予全部业务权限。

## 范围、身份和环境分别判断

| CommandDomain | 执行范围 | 默认允许身份 |
| --- | --- | --- |
| Application | 当前本地应用 | LocalOperator、System |
| World | 单机世界或本机权威服务端世界 | LocalOperator、Player、System |
| Server | 本机正在运行的服务器 | LocalOperator、Player、System |

调用者的 `CommandPrincipalKind` 是单一身份；命令的 `AllowedPrincipals` 使用独立的 `CommandPrincipalKinds` 集合，可进一步声明需要具体玩家数据等身份约束。`HostRequirement` 限定 GUI 或 Headless 环境；`CanExecuteHere` 判断实际执行范围。具备权限不代表世界已加载或服务器已经监听，业务处理器仍检查动态条件。

玩家请求通过 CommandGateway：Application 在玩家所在进程执行，World／Server 在本机权威世界执行或通过 CommandPackage 发往服务器。服务器使用连接绑定的真实 Player 身份与服务器保存的权限。不能由客户端提供操作者身份或授权集合。

本地管理调用使用 `CommandExecutor.ExecuteLocal` 或 `CommandGateway.SubmitLocal`；玩家操作使用 ExecutePlayer／Submit。不能为了方便将玩家管理请求改为 ExecuteLocal。玩家聊天的本地操作者补全仅限 Application 范围，不能混入操作者才能执行的世界／服务器管理命令。

HTTP 宿主提供两组独立入口，沿用 Bearer、显式启用及 loopback 监听：

- `GET/POST /commands`：GUI 与 Headless 的本进程控制入口，使用 LocalOperator。客户端不转发此入口的世界／服务器命令。
- `GET/POST /player/commands`：仅 GUI 提供，要求当前有活动玩家，使用真实 Player。单机／GUI 服务端在本地执行，客户端经 CommandGateway 和 CommandPackage 请求远程服务器。Headless 返回 404，不代表在线的远程玩家调用。

两组入口只暴露显式 HTTP binding。玩家入口只查询及调用 World／Server 命令；远程目录查询通过普通命令取得服务器按该玩家权限过滤的命令标识，再由本地 HTTP 适配器补充参数定义。HTTP 和文本适配器均先构造命令，再通过统一二进制请求发送，服务端按实际连接玩家重新校验。请求体不接受身份、权限或玩家 GUID 来替换当前调用者。客户端文本解析与补全使用不含存档主体记录或授权的输入上下文；它不能作为服务端执行身份，远程补全仍由服务端按实际会话过滤。玩家切换、退出世界或连接断开时尚未完成的请求失效。

POST 使用相同的 identity/arguments 格式；返回 success/code/message/state/data。Pending 表示业务尚未完成，不表示最终成功。请求最多等待 15 秒，超时返回 504；已经送到服务器的操作不能因为 HTTP 超时而撤销，重试前应查询实际状态。HTTP 请求关联 ID 与内部远程请求 ID 分离，迟到回复不会混入聊天或匹配到新的请求。

调用入口使用 Text（玩家文本）、UserInterface、Console、HttpApi 或 Internal 表达，不通过 Mod 标签表达命令归属。模组通过注册所有者及命令命名空间标识归属，与执行身份无关。网络主体通过 FromSession 从实际会话构造；FromPlayer 先解析角色的实际控制会话；本地操作者及系统使用固定主体，不能混入玩家数据或玩家授权。

## 权限执行与授予

具体命令声明 RequiredPermission；未声明时只执行身份和环境检查。已注册权限的检查顺序：LocalOperator／System 放行，随后检查隐式业务授权条件，再检查玩家显式授权。业务隐式条件应明确，例如创造模式玩家可以控制天气；房主身份不是隐式条件。

主体授权包含权限标识及 CanDelegate，并随存档主体记录保存，与角色资产分开。持有使用权不等于可以再授权。

| GrantPolicy | 玩家使用及授权规则 |
| --- | --- |
| Standard | 玩家可获得使用权；有对应再授权能力或标准权限管理能力者可授予 |
| OperatorManaged | 本地操作者可授予玩家使用权；玩家不能继续授权 |
| NonGrantable | 不允许显式授予玩家；只允许本地操作者／系统及权限定义中明确的隐式条件 |

标准权限管理能力不会自动赋予其他业务权限。授权管理者可向自己或其他玩家授予目标权限；再授权能力的授予也受 CanDelegate 校验。

## 非命令功能的边界

领地保护由领地石模组负责；领地归属和授权绑定主体地址，`scnet.territory:admin` 是独立的标准权限。
GUI 房主、首位连接者及角色归属不提供领地权限。调试相机不检查玩家管理权限，沿用创造模式的可用条件。


## 玩家管理目标与封禁

玩家管理命令使用完整玩家身份地址，不把角色名称、角色 ID 或连接短编号当成玩家身份。
`/permission players` 列出存档中的玩家，包含离线及尚未创建角色的玩家；
`/permission list <player>`、`grant <player> <permission>`、`delegate <player> <permission>` 和
`revoke <player> <permission>` 均按已有主体地址定位。省略 `list` 的目标时查询实际调用主体。
传送等角色业务命令继续使用角色名称或角色 ID。

旧玩家面板黑名单已移除。主体业务封禁使用标准权限 `game:server.players.ban`，本地操作者亦可执行：

```text
/player ban <主体地址> "违反存档规则的原因"
/player unban <主体地址>
/player bans
```

封禁原因长度为 1–512 个字符，不允许控制字符；包含空格时需加引号。
封禁保存于本存档的主体记录，记录原因、操作者主体（本地操作者为空）及时间。
服务端在接受连接、恢复角色及下发世界快照前检查封禁，并断开该主体当前会话。
解封保留角色归属、背包及权限，不会恢复已断开的连接，用户需重新连接。GUI 主机玩家的会话被封禁操作断开时，会保存并退出世界，同时停止该 GUI 托管的服务器；可通过 Headless 控制台等可信管理入口解封。
这些命令不操作外部认证服务的封禁。


## 队伍主体与角色列表

`SubsystemTeams` 管理队伍，核心 `TeamStore` 不依赖角色或连接。队伍使用独立 ID，记录队长主体和成员主体地址，不把队长的角色 ID 作为队伍 ID。
创建、加入、邀请、响应和退出均使用实际会话的主体；邀请目标为主体地址。
同一主体最多属于一个队伍，队长退出则解散队伍。断线不取消队籍，离线或尚无角色的主体仍可成为成员。
待处理请求按主体定位响应方，其他主体不能代为接受；请求过期、解散或申请者离线时不会添加成员。

角色不保存队籍。`GetOwnedCharacters` 查询主体拥有的角色；`GetControlledTeamCharacters`
查询同队主体当前控制的角色。玩家面板的同队列表采用后者，因此离线角色不会仅因归属而出现，
角色控制者变化也不会转移原主体的队籍。未来的借用或转移需要额外的角色控制授权，队伍关系不提供该授权。


## 聊天发送者与禁言

聊天请求只携带频道和正文；发送主体从服务端实际会话取得，角色 ID、角色名和主体昵称由服务端在发送时快照。
角色归属不决定发送身份，没有角色的已准入主体也可以发言。消息历史保存完整主体地址和可选角色上下文，
不会因之后改名或切换控制角色而改变。界面显示角色名（如有）、主体昵称（如有）及地址缩写；
地址缩写只用于显示，业务授权和管理仍使用完整地址。队聊按主体队籍选择实际会话，包含尚无角色的在线成员。

主体禁言使用独立标准权限 `game:server.players.mute`，支持离线及尚无角色的玩家：

```text
/player mute <主体地址>
/player unmute <主体地址>
/player muted
```

禁言随本存档主体记录保存，限制全局聊天和队聊，不会因更换受控角色而绕过，也不继承角色所有者的禁言状态。
禁言不阻止正常游戏命令；存档封禁则在命令分发时立即拒绝该主体的世界和服务器命令，不等待会话断开。


## 角色资产与运行编号

角色身体、背包、出生状态和统计属于 `CharacterId`。`CharacterIndex` 是可复用的运行时编号，
用于地形更新等调度，不作为统计或主体身份的持久化键。
`SubsystemCharacterStats.GetCharacterStats` 使用角色 ID；重新创建身体、重连或改变运行编号不会切换统计对象。
私有位置标记属于主体，公共位置标记和信标等按世界位置工作的方块状态属于世界共享数据。
`ComponentBlockEntity.Owner` 保存创建者角色 ID，仅用于发射物或爆炸的角色归因，不是账户访问控制；方块容器内容仍随世界方块实体保存。


## 当前角色界面

游戏菜单的“角色资料”直接编辑当前会话控制的角色。首版一主体最多一角色，
不提供本地添加其他角色、删除角色或通过角色编辑按钮踢人的入口。
名称在同一存档中不区分大小写，客户端预检查包含公开列表中的离线角色，最终仍由服务端裁定。
创建请求只携带资料和独立请求关联 ID，不携带可自行选择的角色身份。
失败响应只回复请求会话；过期或不匹配的响应不能结束新的请求。
创建等待超过 15 秒后可重试，已在服务器创建的角色通过重新连接恢复。
本地权威世界在加载后绑定会话主体，并恢复该主体已存在的离线角色；缺失角色数据时报错，不创建替代角色。


队伍命令的在线校验和提示发送位于命令/网络适配层；核心只验证玩家记录和队伍业务约束。
断线取消未完成邀请或申请但不移除队籍；角色归属或控制者改变也不会转移队籍。


玩家记录通过 `SubsystemPlayers.Store` 访问；角色查询通过 `SubsystemCharacters` 访问。
会话身份和实际控制者通过 `PlayerSessionQuery` 查询，不能从角色所有者推断命令执行者。
公共和私有位置标记由 `SubsystemPositionMarks` 保存；传送等命令仍按实际执行玩家及其权限判定访问。
